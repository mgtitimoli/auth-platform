# Database Guidelines

## Stack

- Kysely (type-safe SQL builder) with the Postgres dialect (`pg`)
- `CamelCasePlugin` maps the database's snake_case to TypeScript's camelCase

## Dependencies

`src/database` imports only from itself, Kysely and `@mgtitimoli/utils`: never
from the domain (`@mgtitimoli/auth-domain`) or the layers above it
(repositories, services, routers).

## Files

- `database.ts`: the Kysely instance and the Postgres pool and dialect
- `database-schema.ts`: the source of truth for the table types
- `*-column-name.ts`: one module per table listing its columns
  (`userColumnNames`, `allUserColumnNames`)
- enum modules (`user-status.ts`): the values of each database enum type
  (`userStatuses`, `UserStatus`), used by `database-schema.ts`
- `kysely.config.ts`: the `kysely-ctl` configuration (migrations and seeds)
- `migrations/`: the migrations
- `seeds/`: the seeds

## Schema Conventions (`database-schema.ts`)

### Table Type Pattern

Tables are named in the plural (`users`), their types in the singular:

```ts
type {Entity}Table = { ... }
type Selectable{Entity} = Selectable<{Entity}Table>
type Insertable{Entity} = Insertable<{Entity}Table>
type Updateable{Entity} = Updateable<{Entity}Table>
```

Add the table to `DatabaseDefinition`, under its name in camelCase
(`userCredentials` for `user_credentials`). Keep keys sorted alphabetically.

### Column Type Modifiers

- `GeneratedAlways<T>`: generated by the database, never inserted or updated
  (`id`, `createdAt`, `updatedAt`)
- `ColumnType<T, T, never>`: set on insert, never updated (`userId`)
- `ColumnType<T, T | undefined, T>`: updatable, with a database default
  (`status`, `loginsCounter`)

Timestamps are `string` (ISO 8601, parsed by `database.ts`). Use `null` (not
`undefined`) for nullable columns, to match the database.

### Column-Name Modules

Repositories select and return columns explicitly, never with `selectAll()` /
`returningAll()`:

```ts
.returning(allUserColumnNames)
```

## Migrations (`migrations/`)

- Naming: `00XXX-description.ts`, exporting `up` and `down`, which take a
  `Kysely<unknown>`.
- Use snake_case (the `CamelCasePlugin` doesn't apply to migrations).
- Use Kysely's schema builder, never raw SQL statements. The only raw SQL is
  inside the `@mgtitimoli/utils/kysely` helpers for what the builder can't do
  (the `updated_at` trigger): call `createSetUpdatedAtTrigger(database, "<table>")`
  for every table with `updated_at`.
- Declare unique constraints in `createTable` with `addUniqueConstraint`,
  named `<table>_<columns>_unique` (repositories recognise violations by that
  name, with `isUniqueViolation`). Prefer unique constraints over unique
  indexes, unless an index-only feature (e.g. a partial index) is needed.
- Never edit or rename a migration once applied: roll it back first.

### Running and Verifying

- `yarn auth-api:run database migrate-all` applies every pending migration of
  the current environment, `database migrate` applies one, and
  `database rollback` reverts the last one applied (another environment:
  `env run --environment <name> yarn database migrate-all`).
- Verify a new migration on `local` by applying it, rolling it back and
  applying it again, so both `up` and `down` run.
- The tests migrate the test database themselves.

## Seeds (`seeds/`)

- Naming: `00XXX-seed-description.ts`, exporting `seed`, which takes the
  `Database`.
- Seeds insert with Kysely directly, declaring their own seed types
  (`AdminUserSeed`), never through repositories or services. A seed that needs
  what a service does (e.g. a user and its credential in one transaction) does
  it itself, with `@mgtitimoli/utils` (e.g. `withPassword.getHash`).
- Seeds are idempotent: they skip what already exists, so they can run more
  than once.
- Run one with `yarn auth-api:run database seed <seed>`.
